# Contributing and upstream review

Start with [development](docs/development.md) for prerequisites, build/bootstrap and the standalone, browser, migration, package and security gates. [Architecture](docs/architecture.md) maps the modules and native boundary. The prepared CI targets native Ubuntu ARM64 and amd64; hosted runs and native amd64 acceptance are still deferred. Keep fixture credentials, databases, output logs and binaries out of commits. `tools/test-pins.env` names the immutable external references.

Run `bash tools/format.sh --write` inside the pinned toolchain before proposing Mojo changes. Generated files are checked by regeneration, not hand formatting. Keep changes focused, explain the user-visible behavior, and record the actual commands and platform results. Include negative regressions for authorization, compatibility, data loss or unsafe-boundary changes. Documentation-only corrections need the publication/link check rather than new application tests.

For an original behavior change, add an independent regression before changing the port. Regenerate rich-text expectations with `tools/regenerate-corpus.sh` against the pinned original image, never from Mojo output. Regenerate `tools/schema_contract.json` and `src/schema_contract.mojo` together with `tools/update_schema_contract.py`. Preserve explicit schema rejection and test both upgrade and current-layout paths. Do not turn reference mismatches into silent exclusions.

`make` regenerates compiled templates from vendored source templates. Include `src/templates.mojo` changes with template edits. The native adapters are an unsafe boundary; changes should run the sanitizer/fuzzer gate as well as relevant HTTP and fault-injection tests. Keep expensive network/decoder/crypto work outside write transactions and retain authorization checks at admission.

Performance results must identify revisions, patches, binaries, image/toolchain, seed, CPU allocation, warmups, repetitions, compression/cache behavior and completed background work. Use `bench/durable.py`, not the historical HTTP-only posting table. Retain every round and failed gate. Do not present the local reference patches as stock Rust/C results.

Before requesting an upstream port/README entry, provide the commit, compatibility matrix, build/test instructions, license/provenance and complete benchmark receipts to the reviewing maintainers. Follow [frontend maintenance](docs/frontend.md) for vendored changes and [local release preparation](docs/releases.md) for candidate exports. Report security issues through the policy in [SECURITY.md](SECURITY.md), never a public issue containing secrets. The release owner and private reporting contact are explicitly deferred; arrange them before a supported public release. No PR, release, registry upload or remote CI is created automatically by the local tooling.
